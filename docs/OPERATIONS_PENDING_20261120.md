## 多云对象存储

管理台“对象存储”提供腾讯云 COS、阿里云 OSS、七牛云 Kodo、AWS S3。每家分别保存桶、地域、访问凭据、公开 HTTPS 地址；勾选“设为默认上传服务”后生效。上传公司、车型、公告图片时，也可临时选择已配置的服务；v2 手机管理台在配置多个服务后弹出选择菜单。

原 COS 配置、环境变量和已有图片 URL 保留。只保存某家配置不会覆盖其他家的凭据；密钥留空保留该家旧值、不回显、继续通过 `installation/settings.key` 加密保存。七牛需填写已绑定的公开 HTTPS 域名；地域使用 z0 / z1 / z2 / na0 / as0 / cn-east-2。AWS 使用标准区域端点（含中国区域），OSS 使用标准地域端点，不接受任意上传 URL。更换默认服务不会移动历史对象。

协议参考：[AWS SigV4](https://docs.aws.amazon.com/AmazonS3/latest/developerguide/sig-v4-header-based-auth.html)、[OSS 官方 SDK 签名实现与测试](https://github.com/aliyun/alibabacloud-oss-php-sdk-v2/blob/master/tests/UnitTests/Signer/SignerV4Test.php)、[七牛上传凭证](https://developer.qiniu.com/kodo/manual/upload-token)。本地测试覆盖官方签名向量、凭据隔离、权限和生成的请求参数；没有使用真实云凭据进行写入联调。

接口继续使用 `/api/admin/media/settings`，增加 `provider=cos|oss|qiniu|s3`（GET 查询或 POST 字段），POST 可带 `activate:true`。`GET /api/media/providers` 登录后返回已配置服务的 ID/名称和默认项，不返回凭据。上传 multipart 可带 `provider`，省略使用默认。旧上传客户端继续可用。

## 下客判断及 MTR 接入

原逻辑只接管上车点：延长该订单的路径副本停站时间，人数满足后等待、关门并释放停站。下车点原来直接使用 MTR 配置的 dwell，所以停留很短时可能乘客还未下车就回库。PHP 展示状态和结算，不决定游戏车门与发车；实际推进在游戏服务器的 MTR Simulator 线程执行。

乘客数据来自 MTR `VehicleExtraData.iterateRidingEntities`，检查 `isOnVehicle()`，由 MTR 客户端的登车/离车更新同步到服务器；不以“附近有没有玩家”判断是否下车。

现在下车点也使用订单独立的停站副本，默认至少开门等待 10 秒（另覆盖门动画），有人则继续等待；服务器连续确认空车 5 秒，才关门并等待关门动画/配置延迟后释放回库。有乘客重新出现会重置空车确认。保持停车只拦截运动计算，保留 MTR 的轨道占用写入与乘客同步。前端完成状态同时等待 `dropoffReleased`，避免一次暂时空车就提前结算完成。人工开门保持停车，人工恢复不能越过下客保护；下车点有人时拒绝关门。

配置在游戏实例 `config/taxilink.json`，旧文件加载时自动补充：

```json
{
  "dropoffMinWaitSeconds": 10,
  "dropoffEmptyConfirmSeconds": 5,
  "obstructionWaitSeconds": 60
}
```

## 管理控制与无站台侧上车

订单详情新增开门并保持停车、关门、手动清除空车，均二次确认并记录审计。物理控制限平台/对应企业管理员，原有紧急停车、恢复和取消保留。清除操作必须空载且静止；车上有人不能强制清除或踢客。回库车辆即使乘客订单已经完成，管理端仍显示车辆跟踪信息。常见模组拒绝原因提供中文提示。

服务端本来就能命令开门，但 MTR 客户端另检查门口附近是否存在站台方块（PlatformHelper）或解锁的站台门/闸门，并据此生成可进入的门区。因此仅服务端强制开门无法让未改动的客户端识别无站台侧登车。

本轮加入可选 TAXILink 客户端 Mixin：乘客安装对应加载器的 TAXILink 与依赖后，在静止、已经开门、且路线号符合 TAXILink 专用 TX 标识时，允许两侧门区通过检查。普通列车不变，不修改 MTR 的 jar。Fabric / NeoForge 按各自 MTR 4.1.0-beta.2 字节码接入；可通过 JVM `-Dtaxilink.disablePlatformlessBoarding=true` 关闭客户端扩展。

这解决的是**侧边站台方块与门区碰撞限制**。上下车停车轨道及 Platform 记录仍供 MTR 寻路、定位和停站使用；本轮不将任意普通轨道变成可作为上下车点的 Platform。车辆资源仍须有有效门区/地板定义。只安装服务端时，客户端侧限制仍存在。

客户端注入已核对两个平台实际目标方法并完成编译，逻辑范围有单元测试；尚未在真实 Minecraft 客户端执行站台侧登车验收，发布前应在测试世界复验，不能把编译通过视为游戏内验收。

## 占轨协助与清除回库车

模组读取 MTR 实际 `railBlockedDistance` 结果，仅在静止、非上下客等待、非人工开门/急停时开始计时，默认持续 60 秒后报告 `assistanceRequired`。业务后端将未结束的订单标为“等待调度协助”；占用解除后只恢复该原因引起的关注状态，不覆盖取消或其他人工关注。

诊断通过 MTR 当前/上一帧 `VehiclePosition.blockedSegments` 查询前方重叠的车辆 ID，再匹配 TAXILink 订单和回库阶段；不以相邻车辆的直线距离猜测。信号占用可能无法定位到具体车辆，这时明确显示未知原因供人工核查，不自动清除车辆。诊断失败不修改正在运行的车辆。

管理端可对匹配到的回库车提交 `clear_blocker`。后端再次校验目标企业管理权限，模组在同一个 Simulator 操作中核对最新占用关系、目标回库阶段、无乘客且静止，再清除目标并恢复目标车厂。目标移动、有人、非回库或占用关系变化均拒绝；不会清除等待订单的车辆。

新增协议 `taxi.clear_returning {orderId,targetOrderId}`；`orderId` 是等待车辆，目标是占用车辆。新旧后端/模组应同步更新，旧模组不支持时返回明确错误，不以本地成功代替执行结果。

## 系统日志与车厂复用

日志支持关键词（请求/连接 ID、指令、结果代码）、通道、事件、结果、精确指令、时间范围组合查询；默认隐藏常规同步的成功记录，搜索请求 ID 时仍能找到它们。提供中文操作含义和常见错误排查说明；现有最多保留 1000 条的策略保留。

车厂流程仍为：报价不占用车厂 → 派车时模组确认专用车厂无活动订单/在途车/乘客 → 保存车厂、停车轨道快照并生成唯一临时路线 → 等待上客、行程、下客 → 空车回库 → 恢复快照、移除临时路线和控制状态 → 下一候补重新校验并派车。**乘客订单完成不代表车辆已回厂或车厂可复用**，后台继续通过 vehicle_pending 跟踪。人工清除也先核验再恢复；重试同一订单保持幂等。

回归已覆盖同一车厂连续四轮完整行程、回库后候补推进、清除回库车不影响等待车厂、有人/移动时拒绝清除、临时空车不提前回库及占轨状态恢复。

本轮验证：业务后端回归通过，管理台构建通过，浏览器回归 4/4 通过（包含 320/390/768 宽度下按钮尺寸与居中检查），v2 H5、Android/iOS Vapor 编译通过；模组 48/48 测试通过（含真实本地 PHP 网关签名 WebSocket 对接），Fabric/NeoForge 编译通过。云存储真实上传与 Minecraft 客户端登车仍待对应测试环境验收。
