# 架构与已确认规则

## 进程与存储

HTTP worker 负责鉴权、管理及乘客 API；`ModGateway` 单进程拥有模组 WebSocket 和请求关联表，内部 RPC 仅监听 127.0.0.1:8789，使用独立随机令牌。`Dispatcher` 单进程负责所有企业候补、模组日志对账及结算，通过进程文件锁防止同一部署重复启动。`PassengerStream` 根据数据库会话鉴权，每两秒推送该用户自己的订单。不能把 Dispatcher 扩展为多个独立实例；多主机扩容前必须引入持久分配仲裁。

订单、候补、快照、邀请、演示支付、日志持久化至 MySQL。SQLite 仅用于本地演示和测试；Redis 用于生产共享限流。常驻进程不共享 PHP 静态连接状态，模组事件先存 `mod_inbox` 再由调度进程消费。网关重启后仍主动查询数据库中的未结束订单、模组状态、分页日志和几何数据。

## 关系与权限

- 一个企业多个中心，一个中心一个企业；本项目进一步禁止同一车厂被多个中心重复使用。
- 每个专用车厂一条停车轨道，多个车厂构成车辆中心。后台中心归属与候补由本仓库管理，不调用模组独立中心队列。
- 一个账号可拥有任意多个 `(企业, 角色)` 成员关系；角色为企业管理员或调度员。平台管理员由配置的 Portal sub 首次登录时精确引导创建。
- 企业管理员可修改本企业中心、车型、范围与费率；调度员可查看本企业订单与执行调度控制。平台管理员创建企业、管理地点与签发邀请。
- 企业成员邀请有效期七天，一次使用，需要受邀人登录后主动接受。移除身份即时影响后续 API 请求。

## 虚拟点

用户只能选择虚拟点，不能直接选择点组。虚拟点映射一条或多条站台；不同虚拟点可共享同一站台。报价自动枚举上下车轨道组合并检查三段连通性，每个车厂/车型保留接客距离最短的有效组合。上下车映射到相同轨道的组合跳过。

企业运营白名单以虚拟点为单位，起终点必须同时在名单。点组批量操作只作用于操作时已有子点，未来新增子点不自动授权。

## 报价与调度

报价有效五分钟，绑定用户、上下车点、人数与所有候选方案。订单确认时保存不可变费率及路线快照。多选企业表示允许其中一个企业承运。一口价可能因各中心调度费不同显示价格范围，实际采用确认报价中的获选方案。

后端为同一业务订单在所有候选中心维护候补关系。全局候补按持久化序号先后处理；每单候选按轨道接客距离排序。使用具体 `depotId/sidingId` 派车，模组执行实际空闲检查。繁忙时尝试下一候选，全部繁忙则继续候补。成功后其余候补立即撤销。暂时离线及超时保留原请求，先对账、再按原单号原参数重试；不得直接换车厂重派。初始候补上限为五分钟，可配置。

## 发车与计费

保留原模组满员或等候超时自动放行，同时支持用户点击“我已上车”调用 `taxi.depart`。不要求绑定游戏 UUID，也不把网页点击当作实际登车证据。

以 `ride.pickup_departure_released` 为精确起点，遥测 ON_TRIP 为暂时缺少日志时的后备；补查日志后修正。首次下车阶段停止计时，回库时长不加入乘客时长。实时里程仅截取 geometry 中 ON_TRIP 路段，调度费分别计算实际几何接客、回库距离的超程部分；轨迹尚未取得时保留报价距离。

金额均为整数分，距离费用按连续里程计算后向上取整至分。接客及回库各自配置免费里程与每千米单价，费用相加。一口价锁定所选方案报价。费率修改只对新报价生效。

先付或预付补退模式按所有入选方案最高预估额演示预付，再参加候补。行程终态先进入 FINALIZING，补齐分页日志与轨迹后结算；多付自动演示退款，少付由收银台演示补付。从未观察到登车且未主动确认发车的完成订单按无人乘车费结算。未派车取消全额退演示预付款，派车后未出发取消按企业取消费；已出发按已发生行程计费。

## 异常

有人乘坐或无法销毁的取消请求转人工协助，不踢出乘客；管理员可以急停、恢复、再次申请取消。模组重启 RECOVERED 转人工协助，不自动二次派车。异步派车失败在补查日志后退还演示预付款。WebSocket 是状态通知，数据库与模组对账负责最终一致性。

## 扩展边界

仅单服务器、单维度；收银台没有真实经济服务实现。未来货币适配器需增加游戏账户选择、真实支付幂等和经济服务对账。底图需采用与当前 X/Z 轨迹相同的投影，接入地图源时不得把示意街区当作实际地理数据。
